Kubernetes node protection · an engineering guide

A private lane for the node.

A Kubernetes worker has two jobs: run application pods, and keep the machinery that runs those pods responsive. If both jobs compete in the same saturated CPU queue, the node can stop making progress even though it still reports Ready.

Node protection gives the host a small, enforceable execution lane. Kubernetes accounts for it, Linux places work into it, the kubelet keeps ordinary pods out of it, and verification proves the contract is active. A memory floor keeps reclaim off the host’s own pages, and a separate storage setting removes a teardown dependency that CPU isolation cannot solve.

01 · The idea

The node must remain able to operate the workload.

CPU utilization answers “was the hardware busy?” It does not answer “could the kubelet and runtime run when they needed to?” Node protection is about promptness and forward progress, not about making a graph look less full.

Utilization is occupancy

A CPU can be 100% busy while serving every task on time. Full is not automatically broken.

CPU pressure is waiting

For a cgroup, CPU PSI reports how often at least one runnable task could not get CPU. It tells us who was delayed.

Lifecycle failure is harm

Runtime deadlines, stuck stops, slow PLEG and runaway pod-start tails determine whether protection is worth its cost.

A reservation by itself is only arithmetic. systemReserved.cpu: "4" reduces allocatable CPU, but it does not pin kubelet to those CPUs and does not prevent a Burstable pod from executing there. The scheduler view and the Linux placement must describe the same boundary.

Why average host CPU can look tiny while the node still misses deadlines

Node work is bursty. A stable pod may need little attention, then one churn event wakes the kubelet, containerd, several shims, CNI helpers, log copying and state observation together. One-minute utilization smooths that moment away; the scheduler still has to serve every runnable task.

The protected lane is an availability mechanism. It does not need to be busy all the time. It needs enough capacity to drain the node’s short, concurrent bursts before runtime deadlines and lifecycle queues begin to compound.
03 · The controls

Four agreements create the CPU boundary.

Each layer has a different authority. Karpenter predicts capacity. The boot script understands physical topology. systemd places host processes. The kubelet places pod containers. Node agents need an explicit exception because they are pods that participate in operating the node.

Capacity accounting

systemReserved.cpu: "4" tells Karpenter and the kubelet that four vCPUs are not available to application scheduling.

Without it: the scheduler can pack work as if all CPUs belonged to pods.

Topology-aware selection

The node reads its online CPUs and sibling map at boot. On an SMT machine, both threads of a physical core stay together.

Without it: a tenant thread can share the same physical core as protected host work.

Host and pod placement

systemd applies AllowedCPUs to host slices. The kubelet’s static CPU manager with strict reservation keeps ordinary containers on the workload set.

Without it: reserved capacity exists on paper but both sides may still execute everywhere.

Node-agent exception

A containerd NRI plugin moves an explicit allowlist of node-agent DaemonSets back onto the protected CPUs at container creation. Chapter 04 explains it.

Without it: CNI, logging and monitoring agents wait beside the saturated tenant.

The CPU lane is only one boundary

Some failures happen while a task is runnable but cannot get CPU. Others happen while a task is sleeping inside the kernel or while memory reclaim reaches the host. Those need controls that match their own failure path.

04 · Node agents

Strict reservation also shuts out the node’s own agents.

The IP address manager (aws-node), kube-proxy, the DNS cache (node-local-dns), the log shipper and the monitoring agents are DaemonSet pods, and strict reservation keeps every pod off the reserved CPUs. Without an exception they wait beside the saturated tenant, and the work they do for the node falls behind: Service routes lag, DNS answers slow, logs and metrics arrive late. A containerd NRI plugin gives a named list of agent DaemonSets the reserved CPUs, and changes nothing but their CPU set.

It matches a DaemonSet, never a namespace

A namespace also holds Deployments, such as CoreDNS and controllers, that would crowd onto four vCPUs. A pod qualifies by the DaemonSet controller’s own name and label, which a hand-made pod would have to imitate (appendix, rule 2).

It changes the CPU set and nothing else

No CPU shares, quota or memory: the kubelet’s values for those apply unchanged. A container the kubelet gave whole CPUs of its own keeps them (appendix, rules 3–5).

It never fails a container

Every failure leaves the container as the kubelet asked. A late reply delays one container by at most 2 s, and then the plugin is dropped (appendix, rules 7–8).

Why a plugin of its own

The kubelet has no exception

Strict reservation keeps every pod off the reserved CPUs, with no per-pod or per-DaemonSet setting. The upstream feature for it, Node System Partition (KEP-5894), is aimed at Kubernetes 1.38 as alpha.

Published NRI policies take over every container

The topology-aware and balloons policies of containers/nri-plugins have a reserved pool, but they place every container on the node, the kubelet CPU manager’s job here. What carries over is their answer to the kubelet’s CPU updates.

A DaemonSet would fight itself

Run as a DaemonSet, the plugin registers again at every rollout and restart, the registration that can freeze the node (containerd#14083), and its own container starts on the saturated workload CPUs.

So the node profile carries a small plugin of its own: about 400 lines of Go on containerd’s NRI library, specified in the appendix precisely enough to build it again.

The plugin’s full specification, sixteen rules with its configuration file, containerd’s NRI settings and a sketch of its four handlers, is in the appendix.

One rule keeps the exception in place, and a restart restores it

Do not restart the plugin from outside containerd. containerd drops a plugin that misses one reply’s 2-second limit (its default plugin_request_timeout) and does not relaunch a plugin it started. Until containerd restarts, new agent containers get the workload CPUs, and running ones keep theirs until the kubelet next updates them. A plugin started from outside must register again, and today a registration can hold every container start and stop on the node until the slowest pod’s graceful stop ends (containerd#14083).

Quiet the serial console, and still expect some drops. Its handlers do almost no work, so a missed reply means the process itself was held up. At the image’s console level nearly every miss came at the end of a node-wide stall at an OOM kill, while the kernel printed the OOM report to the serial console under the lock every other task that runs out of memory waits on; the plugin was alive at every miss, inside containerd’s memory floor and on the reserved CPUs. Under a load built to exhaust memory, on nodes with the memory floor (chapter 05), the plugin was dropped on about 48% of nodes per test at the image’s level and on about 8% with the console at level 4 (chapter 07), about 1 in 200 of the kernel’s OOM reports. The drops left still came at an OOM kill, in the stall before it, which is memory running out. Nodes without the floor dropped it far less often (about 3% per test at the image’s level); whether the floor itself adds drops, beyond its extra OOM kills, was not separated. Watch for its absence and restore it (below).

Recover by restarting containerd. When the per-minute check (chapter 08) reads agent-pin=absent, restart containerd: it relaunches the plugin, which re-pins every listed agent before the kubelet is served again.

List the agents that operate the node, and nothing else

List the IP address manager and its network-policy agent, kube-proxy, the DNS cache, the pod identity agent, the log shipper, the monitoring agents and the node’s own observability agents, not the tenant’s DaemonSets, and never a whole namespace. Their work lands on the reserved CPUs: in testing, nine listed agents used about 0.03 of a core together under load, and across a growing fleet the median node’s reserved CPUs ran 17% busy instead of 5%. Size the lane with that load in it (the starting envelope, chapter 10). The list is written at boot; changing it means replacing nodes.

With the exception, the agents stop waiting and pods start sooner

Under the same CPU-heavy tenant, every agent listed in the comparison waited 84–100% less for CPU with the plugin, and the kubelet and containerd waited no more. Pods started sooner too: the network-policy agent holds a per-workload lock that each sandbox’s network setup waits on, and no longer waits for CPU while holding it.

05 · Memory floor

Reserved CPUs do not reserve memory.

The kubelet’s memory reservation lowers the pods’ ceiling; nothing holds memory for the kubelet and containerd themselves. When the pods fill their share, the kernel reclaims the kubelet’s and containerd’s pages like anyone else’s, and with them the code every pod and node agent runs. A loaded node then freezes in reclaim until an OOM kill, and can go not Ready. A floor, memory.min: memory the kernel will not reclaim from a group. Set by systemd at boot on the kubelet and containerd, it keeps their memory in RAM, as reserved CPUs keep pods off the host’s CPUs.

A page belongs to whoever first brings it into memory

Linux charges a file’s page to the cgroup that first brings it into memory. containerd writes every image when it unpacks it, so the code of every pod and agent sits in RAM as containerd’s memory.

A floor counts only under its parent’s

memory.min keeps what a group uses out of reclaim and caps nothing. The kubelet’s and containerd’s floors take full effect only when runtime.slice, their parent, carries their sum.

A node short of memory freezes; it does not crash

With their code reclaimed, the kubelet, containerd and the kernel write nothing, and the node’s lease goes unrenewed until the kernel’s next OOM kill of a pod ends the freeze: on nodes whose kubelet and containerd had no floor, 9 of 10 lease gaps of 30 seconds or more ended with an OOM kill in their last 20 seconds. A long freeze gets the node marked not Ready, and its pods are not started, stopped or checked until it ends.

Floor the kubelet and containerd

A hard memory.min sized from maxPods and images. The node agents need no floor of their own: their code is containerd’s, and with no swap their working memory cannot be reclaimed.

A floor on the application

It holds the application’s own memory and nothing else. With containerd bare, the node froze and its DNS cache slowed from about a millisecond to up to tens of milliseconds.

06 · Network path

Two network controls protect two different kinds of progress.

A packet can fail because the node has not programmed the Service route yet, or because receive-side kernel work is concentrated on a CPU that cannot drain it fast enough. nftables keeps the Service map current. RPS spreads receive work. RFS tries to follow the reader.

Receive Packet Steering (RPS) hashes flows across a configured CPU mask and queues receive work onto those CPUs. Receive Flow Steering (RFS) adds a table that remembers where the application consuming each flow last ran. That sounds more local, but it depends on the old CPU draining its queued packets before the flow moves.

No receive steering DEFAULT FOR GENERAL NODES

The CPU that receives the packet continues the receive path. This avoids cross-CPU queueing and is the right default when packet processing is not concentrated enough to cause loss.

RPS on workload CPUs SPECIALIST SMALL-PACKET PROFILE

Spread flows across the workload CPU set so packet processing cannot consume the node’s private lane. Enable it only after packet-rate evidence shows a hot receive backlog.

RPS with RFS DISABLED IN THE PROVEN PROFILE

On a saturated node, the application moves while the old CPU’s backlog may never empty. RFS then keeps sending the flow toward the CPU it is waiting to leave, increasing loss.

07 · Configuration

The configuration is layered because the authorities are layered.

There is no single “protect node” flag. The current shape uses an EC2NodeClass for accounting and base kubelet settings, boot-time logic for topology, systemd for host placement and the host’s memory floor, the kubelet CPU manager for pod placement, and NRI for selected node-agent pods.

01

Karpenter plans capacity

The NodePool selects the hardened EC2NodeClass. Four vCPUs are removed from allocatable before pods are packed.

02

The node reads itself

Boot logic groups SMT siblings, chooses complete physical cores and computes the complementary workload set.

03

Linux places the host

system.slice, runtime.slice and init.scope receive the reserved CPU set through systemd, and the kubelet, containerd and runtime.slice their MemoryMin.

04

The kubelet places pods

nodeadm merges the derived CPU list before kubelet starts. Strict reservation becomes the default set for every ordinary container.

05

containerd places agents

NRI changes only the CPU set for named node-agent DaemonSets and leaves every other container unchanged.

Boot script + systemd · memory floor for the host
# memory.min on the kubelet and containerd from maxPods and the
# images' unpacked size; set-property persists across restarts.
MAXPODS=170
IMAGES_MIB=2304
# the kubelet's term: the formula's 200 + a 320 MiB margin = 520
K=$((520 + (3 * MAXPODS + 1) / 2)); C=$((110 + 8 * MAXPODS + IMAGES_MIB))
for u in "kubelet.service $K" "containerd.service $C" "runtime.slice $((K + C))"; do
  systemctl set-property "${u% *}" "MemoryMin=${u#* }M" || echo "node-hardening: memory floor on ${u% *} NOT set" > /dev/kmsg
done
echo "node-hardening: memory-floor kubelet.service=${K}M containerd.service=${C}M runtime.slice=$((K + C))M" > /dev/kmsg

# Left at their defaults: memoryReservationPolicy None,
# enforceNodeAllocatable [pods], no swap. kubeReservedCgroup and
# systemReservedCgroup stay "" as in the Placement layer.
Why it exists: the kubelet’s reservation sets no floor, so reclaim takes the host’s own pages under node-wide pressure. At 170 pods and 2,304 MiB of images this writes 775, 3,774 and 4,549 MiB. MAXPODS follows the class’s maxPods; IMAGES_MIB is the unpacked size of the node pool’s images (du -sm of containerd’s overlayfs snapshots), measured once and re-measured when the images change.
Boot script · serial console log level
# the user data's last lines: the boot lines before them still reach
# the EC2 console output; the journal keeps every level.
echo "node-hardening: console kernel.printk=4 4 1 7" > /dev/kmsg
echo 'kernel.printk = 4 4 1 7' > /etc/sysctl.d/90-console-quiet.conf
sysctl -q -p /etc/sysctl.d/90-console-quiet.conf \
  || echo "node-hardening: console level NOT set" > /dev/kmsg
Why it exists: the EKS AL2023 image sets kernel.printk to 8, so the kernel writes every log level to the serial console, a legacy device it writes synchronously at about 11–15 µs a byte. A global OOM kill prints its report (a header, the memory state and one line per task) while it holds the lock every other task that runs out of memory waits on: about 1 s on a 170-pod node, several seconds with more tasks. At level 4 only errors and more severe levels reach the console: the OOM killer’s Killed process line still does, and the rest of the report goes to the journal, which keeps every level. Under a load built to exhaust memory, on nodes whose OOM report took 4–5 s to print, the node stalled about 3 s less at a comparable OOM kill, the kubelet’s and containerd’s memory stall fell 30–45%, and the agent plugin was dropped on about 8% of nodes per test instead of about 48% (chapter 04). It does not remove the stall before a kill, which is memory running out. Level 5 also prints warnings and unlevelled lines (the OOM header, its stack and the memory state) and keeps only the task list off the console.
Treat this as a coordinated node image, not a live-node tweak. CPU-manager policy, its state file, cgroup placement, memory floors and snapshotter mount behavior are safest to introduce through replacement nodes. A separate NodePool gives rollout, comparison and rollback a clear boundary.

10 · Limits and use

Protect the boundary you actually crossed.

A reserved CPU lane solves node-service scheduling, and the memory floor keeps the host’s own pages out of reclaim. Neither manufactures IP addresses, gives an application more CPU, increases a disk’s throughput or guarantees enough memory for every pod.

The tradeoffs are part of the design

12.5% of a 32-vCPU node

Four protected vCPUs are unavailable to ordinary workloads. Size the lane by failures removed, not by a desire to drive CPU pressure to zero.

Quiet bursts can be slower

When the tenant is idle, host-side pod work is still confined to four vCPUs. The system trades a small quiet-path cost for predictable behavior under saturation.

Rootfs crash durability changes

With overlay volatile, applications must not use the disposable container root filesystem as durable storage.

Pods pay for the memory floor

About 4.4 GiB stays out of reclaim, so a node at its memory ceiling OOM-kills more pods and fails a few percent of health checks instead of freezing.

The agent plugin fails open

If NRI is absent or stops, containers still start. Agents created or updated without it run on the workload CPUs, and the verification signal must alert on that degraded placement.

Use this pattern when…

Pods can saturate every CPU, the node also sees meaningful pod churn, and direct evidence connects kubelet, runtime or node-agent waiting to lifecycle harm.

Re-size or re-test when…

The node shape, SMT layout, NUMA topology, pod density, image path, log volume or peak start/stop wave differs from the validated envelope. The memory floor follows maxPods and the images’ unpacked size: re-compute it when either changes.

Do not use it as a diagnosis when…

The failure says “no addresses,” the application alone is CPU-starved, processes are blocked in I/O, or pods on a floored node are OOM-killed because they outgrew their memory share.

Starting envelope. The four-vCPU lane was sized on 32-vCPU, single-NUMA nodes at 170 pods, using whole physical cores and their SMT siblings. Keep four as the starting point only when the new node class resembles that shape. Add capacity when the protected components still own a real missed objective and the additional CPUs demonstrably move it. The memory floor was measured at 170 pods with 2,304 MiB of images (the formula's values before the kubelet's 320 MiB margin, on the stock 8xlarge; a floor sized from peaks on the hardened one); at other sizes the formula comes from measured memory use, and above 170 pods it is extrapolated.

When an alert fires

01Select one node

Start from the failed lifecycle or packet outcome—not from fleet-average CPU.

02Check the contract

If the live check failed or vanished, drain and replace before diagnosing performance.

03Align the window

Compare the failed operation with CPU wait, kube-proxy sync, softnet, memory and I/O over the same five minutes.

04Route the block

CPU wait, Service-map age, receive drops, full PSI and ENA limits each name a different owner.

05Confirm at the edge

Read the first deadline or packet counter closest to the application; do not infer socket loss from host counters alone.

Do not page on “CPU high.” Saturated workload CPUs are an allowed operating state for this design. Page when protection is absent or a protected node operation is failing; use CPU, memory, I/O and network signals to explain why.
Appendix · The agent plugin

What the plugin must do.

Chapter 04 explains why the node agents need an exception and how the plugin keeps it. This is the plugin itself: sixteen rules for its behaviour, configuration, install, logging and verification, its configuration file, containerd’s NRI settings and a sketch of its four handlers, precisely enough to build it again.

containerd asks the plugin before it creates a container or applies a CPU update, and hands it every running container when it registers. The plugin answers a listed agent’s container with the reserved CPU set and anything else with no change. The contract was built on containerd/nri v0.11.0, the version containerd 2.2.7 vendors, and tested on EKS AL2023 nodes with Kubernetes 1.37.

1EventsImplements the NRI stub’s Configure, Synchronize, CreateContainer and UpdateContainer (ConfigureInterface, SynchronizeInterface, CreateContainerInterface, UpdateContainerInterface; Shutdown only logs). An exclusive container keeps the kubelet’s set.Since Kubernetes 1.33 the kubelet marks exclusive CPUs with quota −1 (DisableCPUQuotaWithExclusiveCPUs, on by default); without that gate the whole-CPU test applies.
4CreateContainerFor a matching container: a ContainerAdjustment with only SetLinuxCPUSetCPUs(reserved), no updates, no error. For anything else: nil, nil, nil.The kubelet’s request carries the shared set; the adjustment replaces it before the container exists.
5UpdateContainerFor a matching container: one ContainerUpdate for its ID with only SetLinuxCPUSetCPUs(reserved) and SetIgnoreFailure(). containerd merges it over the kubelet’s request, so the kubelet’s shares, quota and memory still apply and only its shared set is superseded. 7Fail open
  • CreateContainer, UpdateContainer and Synchronize never return an error.
  • Each recovers from a panic, logs it and leaves the container unchanged.
  • Configure refuses a bad configuration by returning its error, so the plugin never registers.
  • Before Configure, every handler changes nothing.
  • The process exits when the connection closes, and if it is not configured within 30 s.
  • Nothing is ever blocked waiting for it: the default validator and its required plugins stay off.
A handler error fails the container’s creation or the kubelet’s update; a refused configuration, a timeout or a closed connection only drops the plugin. The 30 s exit covers a stub that hangs at boot (containerd/nri#298).
8Reply at once
  • No I/O and no log line in CreateContainer or UpdateContainer: the configuration is parsed once, in Configure, into an atomic pointer; pins are counted in atomics.
  • Never calls the stub’s UpdateContainers: every change rides on a reply.
  • Logs through a summary, once a minute and only when the counts changed. The only lines written while containerd waits for a reply are one at Configure, one at Synchronize and one per panic.

func (p *plugin) Configure(_ context.Context, cfg, _, _ string) (api.EventMask, error) {
	pol, err := ParseConfig(cfg) // rule 9; an error means never registering
	if err != nil { return 0, err }
	p.policy.Store(pol) // and signal the 30 s watchdog (rule 7)
	var mask api.EventMask
	mask.Set(api.Event_CREATE_CONTAINER, api.Event_UPDATE_CONTAINER)
	return mask, nil
}
func (p *plugin) Synchronize(_ context.Context, pods []*api.PodSandbox,
	ctrs []*api.Container) (u []*api.ContainerUpdate, _ error) {
	defer p.recoverInto("Synchronize")
	if pol := p.policy.Load(); pol != nil { u = pol.SyncUpdates(pods, ctrs) }
	return u, nil
}
func (p *plugin) CreateContainer(_ context.Context, pod *api.PodSandbox, c *api.Container) (
	a *api.ContainerAdjustment, _ []*api.ContainerUpdate, _ error) {
	defer p.recoverInto("CreateContainer")
	if pol := p.policy.Load(); pol != nil && pol.Pins(pod, c) {
		a = &api.ContainerAdjustment{}
		a.SetLinuxCPUSetCPUs(pol.Reserved)
	}
	return a, nil, nil
}
func (p *plugin) UpdateContainer(_ context.Context, pod *api.PodSandbox, c *api.Container,
	_ *api.LinuxResources) (u []*api.ContainerUpdate, _ error) {
	defer p.recoverInto("UpdateContainer")
	if pol := p.policy.Load(); pol != nil && pol.Pins(pod, c) {
		u = []*api.ContainerUpdate{pol.Update(c.GetId())} // CPU set + IgnoreFailure
	}
	return u, nil
}
