Where did the request spend its time?

A slow API server is rarely slow everywhere. One request passes through a handful of stages, each owned by someone different: the client, the fairness queue, a webhook, the server's own code, the storage behind it. This guide follows one request through those stages and shows which panel watches each one.

01 · One request, two clocks

The client's clock and the server's clock stop at different places.

A controller sends PATCH pods/web-7f. Follow it through the API server one stage at a time, and watch which stages count towards "what the control plane did" and which only the client feels.

Two numbers at two points

The SLI duration leaves out the fairness queue and the admission webhooks on purpose: those are not the server's own code. When the two lines on the dashboard sit together, look at the server and its storage. When they split, look at the queue and the webhooks first.

Three verbs, three different costs

The dashboard keeps LIST on its own panel because its cost grows with the cluster. A PATCH costs about the same at 100 pods and at 30,000. A LIST of all pods does not.

Read two clocks before reading any one panel: total minus SLI is the time the request spent waiting for a seat or inside a webhook.Everything on the dashboard refines that first split. The latency row tells you which verb and resource; the fairness, admission and storage rows tell you which owner.

Go deeper: what the SLI excludes, the subresource filter, and the scope rule

The SLI metric (apiserver_request_sli_duration_seconds) deliberately excludes admission-webhook execution and priority-and-fairness queue wait. The total (apiserver_request_duration_seconds) includes both. The dashboard draws both on the latency panels so that the subtraction is visible per resource, not only in aggregate.

The subresource filter. Both latency panels drop status, token, scale, /healthz, binding and proxy subresources, and WATCH. Those paths have their own shapes (watches are long-lived by design) and would hide the ordinary request mix.

Scope, not verb, sets the budget. The upstream SLOs are 1 s at p99 for single-object reads and mutations, and 30 s at p99 for namespace- and cluster-scoped reads, both over 5 minutes. The List Latency panel groups by resource only and does not keep scope, so one line can mix a namespaced LIST and a cluster-wide one. Read it as a trend per resource, not as a pass/fail against 30 s.

Within SLO and still a problem. A LIST at 10× the cluster's own usual time can still be inside 30 s. Failure counters, rejection counters and SLO checks all interrogate failure; successful slowness shows on none of them. When those are quiet and a latency line is a large multiple of its own baseline, diagnose against the baseline.

02 · Every millisecond has an owner

Two measurements at two points, and the difference is the diagnosis.

A single latency number cannot say who was slow. Two numbers taken at different points can, because the difference between them is exactly the cost of the layer in between. For a LIST the dashboard gives you three points.

Verdictno action
Confirm withList Latency

Cost is set by what must be examined

A LIST with a label selector walks every object in scope and returns the few that match. The work is the walk, not the answer. The LIST waste factor panel (chapter 04) shows objects walked per object returned.

A healthy etcd percentile does not clear etcd

GETs and LISTs are both range reads to etcd. Thousands of fast GETs dilute a p95 that a few slow LISTs would otherwise raise. Read Etcd Request Latency by operation, and trust the LIST-specific storage panel over the aggregate.

A large encode time usually means a slow client

The API server writes the response while it encodes it. When the client reads slowly, the server waits, and that wait lands in the total with nothing in etcd or decode to show for it. The bottleneck is outside the control plane.

Read the LIST ladder from the outside in: client-observed, then storage-side, then one etcd round trip. Whichever layer holds most of the time owns the problem.Client-observed large, storage small: the time is in the server's own handling or the client. Storage large, etcd small: decode, transform or the selector walk. All three large together: the store itself.

Go deeper: the three rungs, what each includes, and the audit-log view

Rung 1, client-observed: apiserver_request_duration_seconds for LIST. Includes everything: all etcd pages, transformation, filtering, encoding and the write to the client.

Rung 2, storage-side: apiserver_storage_list_duration_seconds. Includes all pages and per-object work (decryption for Secrets) but not request handling or encoding. Emitted only when the LIST goes to storage; a cache-served LIST never touches it.

Rung 3, one page: etcd_request_duration_seconds for list. One round trip to etcd, measured from the API server's side, so it also carries the network between them.

The same split in the audit log. Audit records carry latency annotations: apiserver.latency.k8s.io/etcd (round trips only) and /decode-response-object (API server CPU after the bytes arrived) are separate and may be compared directly; a large decode figure is server-side time, not etcd. /serialize-response-object contains /response-write, so never add those two; when serialize is nearly all write, the client was slow to read. The annotations are a ranking, not a partition: nothing covers the selector walk or the cache freshness wait, and the unexplained remainder is often the majority on selector LISTs.

Who, not what. Metrics carry verb and resource but never the user agent. Once the ladder names a resource, the audit log names the caller: the repo's API Server Diagnostics Guide holds the ready-made queries for top LIST callers and slowest URIs.

03 · Seats, not requests

Capacity is concurrency. Requests per second is the least diagnostic number on the page.

Each API server instance has a fixed number of seats. A request takes a seat for as long as it executes, so a slow request costs more capacity than a fast one. Priority and fairness decides who waits for a seat and who is turned away.

Verdictheadroom

Per instance, not per cluster

Seat limits belong to one API server instance. Two instances can be idle while a third queues, because a client's long-lived connections land on one. The fairness panels keep the instance label for this reason.

Seat demand ≈ rate × seats held × duration

Normal request rate with high latency is a per-request-cost problem (a slow webhook, a big LIST, slow storage), not a capacity problem. High rate with low seat use and no queue is just a busy, healthy server.

Whose traffic is being shaped?

Rejections on workload-low, workload-high or a service-account level are a tenant's own requests being paced: working as designed, fixed on the client. Queueing on a system level, or a level starved by another's long requests, is the control plane's problem.

Capacity is exhausted only when a level queues or rejects while its seats sit at the limit. High latency with seats to spare is cost, not capacity.Rate × cost. If the rate did not change, the cost did: find the request class whose execution time grew.

illustrative
Go deeper: the rest of the fairness row, borrowing, and two negative-evidence rules

Flowcontrol request execution time p90 - Top Instance is the second half of the split: time after the seat was granted. Execution rising while queue wait stays flat sends you to storage, webhooks or the server's own work. Queue wait rising while execution stays flat is a seat shortage.

Rate of addition per second counts requests entering a queue. Near zero when seats are free; a sustained arrival rate means that level is running at its limit continuously, even if nothing is rejected.

Borrowing. Levels lend seats they are not using, which is why the effective limit can sit well above the floor. The floor is the only guaranteed number. Read a level's queue against its effective limit, and read a collapsing limit as neighbours getting busy.

Two rules. First: a webhook holding seats open can saturate a level it is not classified into, so a 429 storm on a system level can still be a customer webhook (chapter 06). Second: fairness counters can be wedged rather than zero; if dispatched requests stop incrementing while clients report 429s, trust the clients and the audit log.

04 · The watch cache

One stream comes in from etcd. Thousands go out.

Every controller and every kubelet keeps a watch open. The API server reads each change from etcd once, keeps a copy in memory, and fans the change out to every watcher. Most reads never reach etcd at all. The cache is what makes a large cluster possible, and it has three ways to hurt.

Verdictcache doing its job

Volume or cost?

Two watch surges can carry the same event count and cost very different amounts. The cost of a reconnect is the replay of initial events to the new watcher; a storm of reconnects against a large resource can hold seats for seconds each. Read the init-events panel beside the active-watches panel.

Old connections or new ones?

Watchers that time out and reopen on an existing connection look different from thousands of new clients arriving. On the dashboard the first shows as init events without a rise in active watches; the second raises both.

Terminated means "could not keep up"

When a watcher reads slower than events arrive, the server closes it rather than buffer forever. The client reconnects and replays. A steady line of terminations on one resource is a slow client, and it costs the server twice.

The watch cache turns one etcd read into thousands of deliveries. When it stops being able to prove it is fresh, reads fall through to etcd and the ladder in chapter 02 starts to matter.Fallback, replay, termination and waste are the four ways the cache stops saving work. Each has its own panel.

Read it: a ratio near 1 means LISTs return what they walk. A ratio of 40 means every returned object cost forty object evaluations: a client is asking for a small answer with a label or field selector over a large collection, in the cache or in storage. The work is the walk, and no latency annotation will ever show it. Pair this with List Latency for the resource and the audit log for the caller.

illustrative
Go deeper: consistent reads, active watches, terminated watchers, and freshness

Consistent reads: cache vs fallback-to-etcd. A read that asks for the latest state (no resourceVersion) can still be served from the cache if the cache can prove it is current. When it cannot, the read falls back to etcd. A rising fallback line means the cache is lagging the store, and every such read pays the full ladder.

Active watches by resource (top 10). Long-running WATCH requests by resource. The expected shape is stable and explained by the controllers you know you run. A step up on one resource is a new watch-heavy client; the audit log names it.

Terminated watchers by resource. Watchers closed by the server because they fell behind. Expected to be empty.

Freshness has a hard wait. A read that needs the cache to catch up to a given version waits for a bounded time before failing. Latency that clusters at a constant few seconds on reads, with nothing in etcd or decode, can be that wait rather than a webhook; the round number tells you a limit was hit, not whose (chapter 06).

Request-side test for cache versus storage. A LIST with resourceVersion=0 in the request URI accepts a cached answer; one without demands the latest. That parameter is in the audit log's requestURI and is a sounder test than the absence of an etcd annotation.

05 · Storage, the client view

You cannot tune the store. You can see what you are asking of it.

On a managed control plane the storage backend is not yours to size, defragment or re-elect. What you can see is the API server's own view as a client: how big the store is, what fills it, how long its LISTs take and whether its calls fail. Every fix on this row lives on the client side.

Writes are usually someone's loop

Sustained mutation storms come from a short list of patterns: certificate or secret rotation tools, logging and monitoring agents rewriting ConfigMaps, lease renewals from a very large node count, and custom controllers reconciling too eagerly. The audit log's "top mutating operations" query names the user agent.

Size drives three other panels

A collection that grows without a plateau shows up again as rising List Latency for that resource, larger Response sizes, and climbing API Pod Memory, because the cache holds a copy of every object. Read growth here first; it explains the others.

Storage errors are distinct from fairness rejections, and storage slowness is distinct from both. This row tells them apart; the fix for all three is to change what clients ask.The managed store's internals (disk, compaction, leadership) are not on this dashboard because you cannot act on them. What you ask of it, you can.

Go deeper: Storage DB size, the storage LIST panel, and what is left off on purpose

Storage DB size (client-reported) is the store's size as the API server learns it. Healthy growth is slow and reaches plateaus. Persistent acceleration together with rising storage latency is the pair to escalate on; size alone is context.

Storage LIST duration p99 by resource appeared in chapter 02 as rung two of the ladder. It belongs to this row on the dashboard.

What is not here on purpose. Backend disk latency, compaction, defragmentation and leader elections are managed and not customer-tunable; the dashboard shows the API server's view (Etcd Request Latency, errors, size) because that view is both observable and actionable through client behaviour.

06 · The front door and the webhooks

Before the handler runs, and before storage is touched, two other kinds of code get a say.

Identity checks run first: a TLS handshake, then authentication, then authorisation, then a chain of filters. For writes, admission webhooks run next, and they are code you installed, not the API server. The dashboard separates each so a slow or failing stage has a name.

A 401 proves the request arrived

A 401 with an empty user is authentication; a 403 with a named user is authorisation; no record at all means it never reached the server. The source address and user agent survive a 401, so the caller stays attributable.

A round number is a limit, not a measurement

Latency pinned at exactly 1 s, 10 s or 30 s means some timeout fired. It does not say whose: the handler's, the webhook's, or the cache's freshness wait all produce the shape. The webhook panel, by name, is what attributes it.

Three ways a webhook hurts

It can be slow (writes wait, 504s on timeout). It can hold seats (a fairness level saturates and sheds 429s). It can fail closed (every CREATE is refused and no pod ever reaches Pending). Each shows on a different row.

Identity, filters and webhooks each add time before the handler runs. The webhooks are the only stage the SLI leaves out and the only stage you installed yourself.When total and SLI split on writes and the fairness queue is quiet, the webhook panel will have the name.

Go deeper: AuthN / AuthZ duration, TLS and aborts, outbound client errors, and the webhook evidence chain

AuthN / AuthZ duration p99. Two lines. Authentication alone rising points at the authenticator path (token review, identity provider); authorisation alone rising points at policy evaluation.

TLS handshake errors + request aborts. Handshake errors are clients failing before any request exists (certificate, protocol, or a connection cut short). Aborts, by verb, are requests the server stopped mid-flight. Both are expected to be empty.

API server outbound client errors (rest_client, non-2xx). The API server is itself a client of webhooks and aggregated APIs. Non-2xx responses here, especially 5xx, mean a dependency you installed is failing, which is the mechanism behind cascading 500s on the resources it serves.

Establishing that a webhook is the cause. A 504 with context deadline exceeded on a write; the webhook's name in the duration panel; the configured timeout visible in the failing request's URL (?timeout=10s); and, for fail-closed, a workload with zero Pending pods because the CREATEs never got far enough to schedule. Search the audit log by shape (verb, resource, code), not by rank within the hour you were paged for; the evidence is often in a different verb or an earlier hour.

07 · The process itself

Instances should move together. The one that does not is the story.

Behind the request path is an ordinary process: memory full of cached objects, CPU spent encoding and decoding, threads parked on slow calls, a count of requests in flight, and a count of requests it gave up on. The dashboard draws these per instance so that one diverging line stands out.

Memory follows the cache

Resident memory is mostly cached objects plus the responses being built. Plateaus that step up with cluster growth are normal. A climb that never flattens, or one instance far from its peers, is a large collection or an unusually heavy client pinned to that instance.

Threads ratchet when calls block

Go uses operating-system threads sparingly; the count only grows when many calls are parked waiting. A thread count that steps up and does not come back corroborates blocked storage or webhook calls in the same minutes.

Terminations count failure. Slowness is not failure.

A termination is a request the server abandoned. The counter is the right page. It is also silent on every request that succeeded slowly, which is why the latency panels exist.

A healthy control plane is three similar lines. Read every per-instance panel for divergence first and level second.A ceiling that all lines flatten against is capacity. One line away from the others is a client, a collection or a dependency that landed on that instance.

08 · Walk the dashboard

Now the dashboard reads as a sequence of questions.

Every chapter added one owner. The dashboard's rows map onto them: two clocks and a request class at the top, then fairness, the cache, storage and admission as the places time can go. Pick an incident and watch the path light up.

Use the one variable

The dashboard has a single $job selector; everything else is per instance in the legends. When one instance is the story, read its legend entry across every panel before averaging anything.

Do not page on rate

Request rate and CPU rise with a healthy cluster. Page on terminations, rejections on system levels, storage errors, unavailable APIServices, and total latency that is a large multiple of its own baseline. Everything else explains; it does not alarm.

Leave with one request class, one window, the stage that held it and the owner of that stage."The API server was slow" is not a diagnosis. "LIST pods with a label selector from one controller walked 40 objects per returned object from 14:02 to 14:20; storage was idle" is.
